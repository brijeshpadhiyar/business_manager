## 1. Existing Architecture Analysis

Before V1.3, StitchFlow modeled production via:
- `lots` -> `lot_designs` -> `design_colours` (Production Orders / Jobs and SKU initial quantities).
- `processes` & `members` (Master list of dynamic operations and workers/departments).
- `stock_movements` (Append-only ledger of `ISSUE`, `RETURN_GOOD`, `RETURN_DAMAGED`, `SETTLEMENT_LOST`, `SETTLEMENT_SHORTAGE`, `ADJUSTMENT_DAMAGED_TO_GOOD`, and `REVERSAL`).

**Limitation Identified:**
Users could only issue stock from Factory to a worker and settle it back to Factory one movement at a time. There was no Job-level multi-operation tracker (`job_processes`), no independent operation status lifecycle, no direct worker-to-worker material handover (`Factory -> Dharmesh Cutting -> Packing Department`), no partial split routing (`300 Direct Transfer + 150 Factory Return + 50 Pending`), and no chronological Job Movement Timeline with unique transfer references and receipt confirmations.

## 2. Database Changes (Schema v4)

Two strictly relational, foreign-key-enforced tables were added in `lib/core/database/tables/job_process_tables.dart`, registered in `AppDatabase` (`schemaVersion = 4`), and migrated safely via `DatabaseMigrationManager.handleOnUpgrade` (`from < 4`) without altering or deleting any existing table or record.

### Table `job_processes`
Tracks unlimited operations per Job (`lot_id` + `design_colour_id`), allowing repeated operations and flexible non-linear ordering:
- **Foreign Keys (`ON DELETE RESTRICT`)**: `lot_id -> lots(id)`, `lot_design_id -> lot_designs(id)`, `design_colour_id -> design_colours(id)`, `process_id -> processes(id)`, `member_id -> members(id)`, `source_job_process_id -> job_processes(id)`, `linked_issue_movement_id -> stock_movements(id)`.
- **Quantities**: `planned_quantity (> 0)`, `dispatched_quantity`, `received_quantity`, `returned_to_factory_quantity`, `transferred_out_quantity`, `damaged_quantity`.
- **Independent Statuses (`CHECK` constrained)**: `DRAFT`, `PENDING`, `DISPATCHED`, `IN_PROGRESS`, `PARTIALLY_COMPLETED`, `COMPLETED`, `PARTIALLY_RETURNED`, `RETURNED`, `TRANSFERRED`, `CANCELLED`.

### Table `process_handovers`
Immutable chronological movement & transfer ledger for every Job:
- **Identifiers**: `id`, `transfer_reference` (`UNIQUE`), `client_request_id` (`UNIQUE WHERE NOT NULL` for duplicate prevention).
- **Foreign Keys (`ON DELETE RESTRICT`)**: `lot_id`, `lot_design_id`, `design_colour_id`, `from_job_process_id`, `to_job_process_id`, `from_member_id` (null = Factory), `to_member_id` (null = Factory), `process_id`, `linked_stock_movement_id`.
- **Types (`CHECK` constrained)**: `FACTORY_DISPATCH`, `DIRECT_TRANSFER`, `FACTORY_RETURN`, `REASSIGNMENT`, `CANCELLATION`.
- **Receipt Tracking**: `quantity_dispatched`, `quantity_received (<= quantity_dispatched)`, `status` (`PENDING_RECEIPT`, `PARTIALLY_RECEIVED`, `RECEIVED`, `CANCELLED`).

### Additive v4 Indexes (`SchemaIndexes.v4IndexStatements`)
- `idx_jp_lot_seq`, `idx_jp_design_colour`, `idx_jp_member_status`
- `idx_ph_transfer_ref` (`UNIQUE`), `idx_ph_client_request_id` (`UNIQUE PARTIAL`)
- `idx_ph_lot_tx`, `idx_ph_from_member`, `idx_ph_to_member`

## 3. Workflow Design, Routing & Worker Handover Logic

### Zero Conflicting Inventory System
All stock-moving actions execute inside a single atomic SQLite transaction (`DatabaseTransactionRunner.runInTransaction`) and reuse StitchFlow's existing append-only `stock_movements` + `labour_entries` + `audit_logs` ledger:

1. **Scenario A — Direct Worker-to-Worker Transfer (`Factory -> Dharmesh Cutting -> Packing Department`)**:
   - Validates `transferQty <= sourceProcess.pendingQuantity`.
   - Atomically settles `transferQty` (`RETURN_GOOD`) against Dharmesh's linked `ISSUE` movement (updating Dharmesh's stock & labour history) AND immediately issues `transferQty` (`ISSUE`) to Packing Department.
   - Net Factory in-house stock stays conserved (`0` change); Dharmesh's pending drops by `transferQty`; Packing Department's new operation receives `dispatched = transferQty`.
   - Inserts a `DIRECT_TRANSFER` handover with a unique `TRF-YYYYMMDD-XXXXXXXX` reference. Destination confirms full or partial receipt (`confirmHandoverReceipt`).

2. **Scenario B — Return to Factory & Reassignment (`Factory -> Dharmesh -> Factory -> Packing Worker`)**:
   - `returnToFactory`: Validates `goodQty + damagedQty <= sourceProcess.pendingQuantity`, posts settlement (`RETURN_GOOD` / `RETURN_DAMAGED`) into `stock_movements` (increasing Factory `physicalAvailableInHouse`), updates source status (`RETURNED` / `PARTIALLY_RETURNED`), and logs a `FACTORY_RETURN` handover (`RET-...`).
   - `reassignFromFactory`: Validates `reassignQty <= physicalAvailableInHouse`, posts a new `ISSUE` in `stock_movements`, creates a new `job_processes` operation for the Packing Worker, and logs a `REASSIGNMENT` handover (`RAS-...`).

3. **Scenario C — Partial Split (`500 -> 300 Direct Transfer + 150 Factory Return + 50 Pending`)**:
   - All quantities reconcile independently: `pendingQuantity = dispatchedQuantity - returnedToFactoryQuantity - transferredOutQuantity - damagedQuantity`.
   - Conservation holds at every step: `Factory (150) + Packing (300) + Dharmesh (50) = 500`.

## 4. Strict Validation Rules (`ProcessRoutingValidator`)

1. Cannot dispatch more than available in-house Factory quantity (`insufficient_good_stock`).
2. Cannot receive more than dispatched quantity (`exceeds_dispatched_quantity`).
3. Cannot transfer stock not currently held by the source worker (`exceeds_held_quantity`).
4. Cannot return more than the outstanding worker quantity (`exceeds_pending_quantity`).
5. Cannot reassign unavailable Factory quantity (`insufficient_good_stock`).
6. Cannot mark a process Completed while pending quantity remains unaccounted (`unaccounted_quantity_remaining`).
7. Partial transfers, partial returns, and partial receipts are first-class and independently tracked.
8. Every handover generates a globally unique reference using the random entropy tail of UUIDv7 (`DSP-`, `TRF-`, `RET-`, `RAS-`, `CNL-`).
9. Duplicate submissions are prevented via `clientRequestId` unique partial index & idempotent replay.
10. Required SKU, operation, worker, positive quantity, and damage/cancellation reasons are strictly validated.
